## 1. Project Context & Tech Stack

### 1.1 Project Overview

This project implements a **domain-specific Retrieval-Augmented Generation (RAG) system** targeting diabetes research in children and adolescents. The system ingests biomedical research abstracts, generates dense vector embeddings using a biomedical-specific transformer model (**MedCPT**), stores them in a vector database (**ChromaDB**), and enables semantic search with natural-language answers generated by an LLM (**Groq API / GPT-OSS-20B**).

### 1.2 Technical Goals

1. Build a knowledge base from 44 biomedical research abstracts on pediatric diabetes.
2. Use **asymmetric dense retrieval** — separate encoder models for articles and queries — via the MedCPT family of models from NCBI.
3. Persist vector embeddings in a local ChromaDB instance for efficient cosine-similarity search.
4. Implement a **RAG pipeline** that retrieves relevant documents and generates grounded answers via an external LLM API.
5. Validate the chunking strategy to ensure no information is silently truncated during embedding.

### 3.2 Key Architectural Decisions

#### A. Asymmetric Dense Retrieval (MedCPT)

**Decision:** Use two separate encoder models — `MedCPT-Article-Encoder` for documents and `MedCPT-Query-Encoder` for questions.

**Rationale:** MedCPT was trained with contrastive learning on PubMed query-article pairs. The article encoder expects `[title, abstract]` pairs, while the query encoder expects plain-text queries. This asymmetric design better captures the semantic gap between how medical knowledge is expressed in papers versus how clinicians/patients phrase questions.

#### B. ChromaDB with Persistent Storage

**Decision:** Use `chromadb.PersistentClient` with local SQLite storage at `./vector_db`.

**Rationale:** Eliminates the need for a separate database server. Embeddings persist across sessions without re-ingestion. The HNSW index enables fast approximate nearest-neighbor search. Cosine similarity was chosen as the distance metric because MedCPT embeddings are not L2-normalized, and cosine distance is invariant to vector magnitude.

#### C. Adaptive Sentence-Boundary Chunking

**Decision:** Split documents at sentence boundaries (`. ` delimiter) with a 2,000-character maximum chunk size.

**Rationale:** MedCPT's maximum input is 512 tokens. Biomedical text averages ~4-5 characters per token, so 2,000 characters translates to approximately 400-500 tokens — safely within the limit. Sentence-boundary splitting preserves semantic coherence better than fixed-window chunking. The tokenizer's `truncation=True` acts as a safety net for edge cases.

#### D. Deterministic Chunk IDs

**Decision:** Use IDs formatted as `{filename_stem}_chunk_{index}` (e.g., `myfile_chunk_0`).

**Rationale:** Deterministic IDs enable idempotent `upsert` operations — the ingestion script can be re-run without creating duplicate entries in ChromaDB.

#### E. Environment-Variable API Keys

**Decision:** Store `GROQ_API_KEY` in `.env` and load via `python-dotenv`.

**Rationale:** Prevents accidental exposure of API credentials in version control. The `.env` file is listed in `.gitignore`.

#### Step 1.1 — Load MedCPT Article Encoder

**Objective:** Download and initialize the MedCPT Article Encoder model from HuggingFace.

**File Created:** `ingest.py`

**Core Logic:**

```python
from transformers import AutoTokenizer, AutoModel

ARTICLE_MODEL_NAME = "ncbi/MedCPT-Article-Encoder"

tokenizer = AutoTokenizer.from_pretrained(ARTICLE_MODEL_NAME)
model = AutoModel.from_pretrained(ARTICLE_MODEL_NAME)
model.eval()
```

- `AutoTokenizer` loads the BERT-based tokenizer for MedCPT.
- `AutoModel` loads the pre-trained transformer weights.
- `model.eval()` disables dropout and batch normalization layers — critical for deterministic inference.

**Design Rationale:** `AutoTokenizer`/`AutoModel` are used instead of specific classes (e.g., `BertModel`) to keep the code model-agnostic. If NCBI releases an updated encoder architecture, only the model name string needs to change.

---

#### Step 1.2 — Define the Embedding Function

**Objective:** Create a reusable function to generate 768-dimensional embeddings from text chunks.

**File Modified:** `ingest.py`

**Core Logic:**

```python
def generate_embedding(text, title=""):
    encoded = tokenizer(
        [[title, text]],
        truncation=True,
        padding=True,
        return_tensors="pt",
        max_length=512,
    )

    with torch.no_grad():
        output = model(**encoded)

    cls_embedding = output.last_hidden_state[:, 0, :]
    embedding_list = cls_embedding.squeeze().numpy().tolist()
    return embedding_list
```

**Key Implementation Details:**

| Parameter | Value | Why |
|-----------|-------|-----|
| `[[title, text]]` | Nested list of `[title, abstract]` pair | MedCPT Article Encoder was trained on title-abstract pairs |
| `truncation=True` | Clips to `max_length` | Safety net for chunks slightly exceeding 512 tokens |
| `max_length=512` | MedCPT's context window | BERT-based models have a fixed positional embedding limit |
| `torch.no_grad()` | Disables gradient computation | Saves memory and compute during inference |
| `last_hidden_state[:, 0, :]` | CLS token extraction | The `[CLS]` token's representation is the pooled embedding |
| `.squeeze().numpy().tolist()` | Shape `(1, 768)` -> Python list | ChromaDB expects plain Python lists, not tensors |

**Design Rationale:** The `title` parameter defaults to `""` (empty string) because the current knowledge base contains only abstracts without associated titles. The function signature was designed to support future title-enriched ingestion without code changes.

#### Step 1.7 — Adaptive Sentence-Boundary Chunking

**Objective:** Split long texts into chunks that fit within MedCPT's 512-token context window.

**File Modified:** `ingest.py`

**Core Logic:**

```python
MAX_CHUNK_SIZE = 2000  # characters

def create_chunks(text, max_size=MAX_CHUNK_SIZE):
    if len(text) <= max_size:
        return [text]

    sentences = text.split(". ")
    chunks = []
    current_chunk = ""

    for sentence in sentences:
        sentence = sentence.strip()
        if not sentence:
            continue

        if len(current_chunk) + len(sentence) + 1 <= max_size:
            current_chunk += sentence + ". "
        else:
            if current_chunk:
                chunks.append(current_chunk.strip())
            current_chunk = sentence + ". "

    if current_chunk:
        chunks.append(current_chunk.strip())

    return chunks
```

**Design Rationale:**

- **`MAX_CHUNK_SIZE = 2000`** — Reduced from an initial value of 3,000 to stay safely within MedCPT's 512-token limit. At ~4-5 characters per token for biomedical text, 2,000 chars = 400-500 tokens.
- **Sentence-boundary splitting** — Splitting on `". "` preserves sentence integrity. Fixed-window chunking would break mid-sentence, destroying semantic meaning.
- **Short-text passthrough** — Abstracts shorter than 2,000 characters (the majority) are kept as single chunks to avoid unnecessary fragmentation.

#### Step 2.3 — Query Encoding Function

**Objective:** Encode a user's natural-language question into a 768-dim vector.

**File Modified:** `query.py`

**Core Logic:**

```python
def encode_query(question):
    encoded = query_tokenizer(
        [question],            # Simple string list (NOT [title, abstract] pairs)
        truncation=True,
        padding=True,
        return_tensors="pt",
        max_length=512,
    )

    with torch.no_grad():
        output = query_model(**encoded)

    query_embedding = (
        output.last_hidden_state[:, 0, :]
        .squeeze().numpy().tolist()
    )
    return query_embedding
```

**Key Difference from Article Encoder:** The query encoder expects a flat list of strings `[question]`, not `[[title, abstract]]` pairs. This matches MedCPT's training objective where queries are short plain-text questions.

#### Step 2.6 — RAG Response Generation (Groq LLM)

**Objective:** Send retrieved documents as context to an LLM API and generate a grounded answer.

**File Modified:** `query.py`

**Core Logic:**

```python
def generate_rag_response(question, results, api_key):
    docs = results["documents"][0]
    context = "\n\n".join(
        [f"Document {i+1}:\n{doc}" for i, doc in enumerate(docs)]
    )

    system_prompt = (
        "You are a helpful medical assistant specializing in "
        "diabetes for children and adolescents. "
        "Use ONLY the provided context to answer..."
    )

    user_prompt = (
        f"Context information is below.\n...\n{context}\n...\n"
        f"Question: {question}\nAnswer:"
    )

    url = "https://api.groq.com/openai/v1/chat/completions"
    headers = {
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json"
    }
    payload = {
        "model": "openai/gpt-oss-20b",
        "messages": [
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        "temperature": 0.2
    }

    response = requests.post(url, headers=headers, json=payload)
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"]
```

**Design Rationale:**

| Decision | Rationale |
|----------|-----------|
| `temperature: 0.2` | Low temperature for factual, grounded answers — the LLM should not hallucinate beyond the context |
| System prompt restricts answers to context | Prevents the model from using its pre-training knowledge, ensuring answers are traceable to source documents |
| Groq API (OpenAI-compatible) | Free tier, fast inference, supports the `openai/gpt-oss-20b` model |
| Graceful API key handling | If `GROQ_API_KEY` is unset, the function returns a message instead of crashing |

## 5. Challenges, Errors & Solutions

### 5.1 Embedding Dimension Mismatch

**Problem:** When switching from the initial model (`all-MiniLM-L6-v2`, 384-dim) to `MedCPT-Article-Encoder` (768-dim), ChromaDB rejected new embeddings because the existing HNSW index was built for 384 dimensions.

**Error:** ChromaDB dimension mismatch error during `upsert`.

**Fix:** Added a `delete_collection()` call in `ingest.py` to wipe the old collection before re-indexing:

```python
try:
    client.delete_collection(name="research_abstracts")
except Exception:
    pass
```

### 5.2 Windows Console Unicode Errors

**Problem:** Printing biomedical text containing Unicode characters (e.g., plus-minus sign, micro sign, greater-than-or-equal sign) to the Windows PowerShell console raised `UnicodeEncodeError` because the default encoding is `cp1252`.

**Fix:** Forced UTF-8 encoding on stdout at the top of affected scripts:

```python
import sys, io
sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8")
```

Applied to: `inspect_db.py`, `validate_chunks.py`, `verify_embedding_storage.py`.

### 5.3 Chunk Size Calibration

**Problem:** The initial `MAX_CHUNK_SIZE` of 3,000 characters risked exceeding MedCPT's 512-token limit for dense biomedical text.

**Diagnostic:** Calculated the character-to-token ratio for biomedical text: ~4-5 characters per token. At 3,000 characters, chunks could reach 600-750 tokens — well beyond the 512-token limit.

**Fix:** Reduced `MAX_CHUNK_SIZE` to 2,000 characters. At ~4-5 chars/token, this yields 400-500 tokens per chunk, safely within the limit. Validated post-fix: maximum observed token count was 300 (well under 512).

### 5.4 Hardcoded API Key

**Problem:** The Groq API key was hardcoded directly in `query.py`, creating a security risk if the file were committed to a public repository.

**Fix:**
1. Created `.env` file with `GROQ_API_KEY` variable.
2. Added `python-dotenv` dependency.
3. Refactored `query.py` to use `load_dotenv()` + `os.getenv("GROQ_API_KEY")`.
4. Added `.env` to `.gitignore`.
